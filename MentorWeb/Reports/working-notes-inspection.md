## Aggregates

Aggregate that loads the Employee records on the list screen:

- Name: **GetEmployees** (screen aggregate on screen **Employees**). Use this name in the task 5 prompts.
- Fetch: At start. Source: entity Employee only (no joins). Sort: TableSort screen variable.
- Paging: screen variable MaxRecords default 10, StartIndex default 0. A Pagination block is on the screen. The table shows 10 rows per page by default.
- Filter 1 (search): a single condition, OR-ed:
  - `SearchKeyword = ""` (empty-string literal, length 0)
  - or `Employee.FirstName like ("%"-style literal + SearchKeyword + literal)`
  - or `Employee.LastName like (...)`
  - or `Employee.JobTitle like (...)`
  - or `Employee.Email like (...)`
  - The wildcard literals have length 1 and hash 4345cb1fa2, which equals the SHA-1 prefix of "%". The literal text itself is not readable from the graph.
- Filter 2 (role check): `CheckStaffRole(UserId) or CheckStaffRole(UserId) or CheckAdminRole(UserId)`.
- **No filter on Employee.IsActive exists in GetEmployees.** The only IsActive references in the whole app are in the entity, the EmployeeStructure structure, the ExcelDownload record-list-to-excel attribute, the sample-data record literals and one display on Employee_Details.
- Local screen variables on Employees: StartIndex, MaxRecords, SearchKeyword, TableSort.
- Screen actions on Employees: OnPaginationNavigate, OnSearch, OnSort. A search input (Search block, input widget Input_TextVar) is present and bound to SearchKeyword through OnSearch. I did not trace OnSearch step by step.

Aggregate that loads one employee on the detail screen:

- Name: **GetEmployeeById** (screen aggregate on screen Employee_Details).
- Filter 1: `Employee.Id = EmployeeId`. Filter 2: the same role check as above (Staff or Admin).
- No IsActive filter.

Other aggregates (server actions, not screens): GetEmployee (in DownloadEmployeeExcel), Count (in UploadEmployeeExcel), TryGetNameByEmail (in SendResetPasswordEmail), GetEmployeeRecords (in LoadSampleData). Data actions: GetShowImportData, GetShowLoginAs.

## Employee data

Facts that **cannot be read** with the read-only tools available:

- The number of Employee records: not readable.
- The number of records with IsActive = false: not readable.
- Whether an active employee with FirstName Alice exists: not readable.
- Reason: the MCP read tools expose the model (entities, screens, actions, graph) but no data query. The sample-data JSON is a text literal that `context_graph` hides.

Facts about how sample data gets loaded:

- Server action **LoadSampleData** (description "Load Sample Data Generated by AI"). It has an If node labelled "GetEmployeeRecords.List.Empty and IsInDevStage()?". It reads the Employee table (aggregate GetEmployeeRecords) and calls LoadSampleDataForEmployee only when the table is empty and the stage is development.
- Server action **LoadSampleDataForEmployee** ("Load Sample Data for Employee, Generated by AI"). It deserializes a JSON text into an Employee list (JSONDeserializeEmployeeList), loops over it and calls CreateEmployee. The JSON text is not readable, so the record count, the IsActive values and the names are unknown.
- Timer **LoadSampleDataOnPublish** ("Load Sample Data on publish") exists in the app (key 714bdcab-77b8-0393-1deb-ab1b53d511c1). The timer's schedule, and whether it has run, were not read. I did not find a call to LoadSampleData in the graph of the Employees screen, and the timer's wiring was not traced.
- `IsInDevStage` is a server action in the app. Its logic was not traced.
- Whether the data currently exists in the tenant is therefore unknown from read-only calls. It needs a look in ODC Studio or the browser (AC-06 says "inspected in ODC Studio or the browser").
